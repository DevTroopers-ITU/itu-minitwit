# Findings — known weaknesses & "what we'd improve"

Honest list of issues caught during exam prep, all verified against the code/prod (not guesses).
Good ammo for the **Reflection** perspective: "things slipped in fast during weekly delivery; here's what we'd fix with more time."

## Security
- **Prod session key is the public hardcoded fallback (CONFIRMED LIVE 1 Jun 2026).** `getSecretKey()` only reads `SECRET_KEY` when a `.env` file exists; prod containers have none → returns `"dev-fallback-key-change-in-production"`. The real `secret_key` Docker secret is mounted at `/run/secrets/secret_key` but never **reached** — `getSecretOrEnv` *would* read it correctly, but the call is gated behind a `.env` check (`godotenv.Load()`) that fails in prod, so the lookup is skipped. (Ironically commit `442ddbb` "fix: lowercase secret path to match Docker Swarm mount name" wired the path correctly — but it's still unreachable.) → Anyone reading the repo can forge login cookies and impersonate any user.
  - Made worse by `sessions.NewCookieStore([]byte(SECRET_KEY))` using **one key** = cookies are signed but NOT encrypted, and they just hold `user_id`. Forge `user_id`, sign with the known key, you're that user.
  - Fix: read `SECRET_KEY` directly via `getSecretOrEnv` (not gated behind `.env`); fail loudly if missing; set a strong secret; consider also encrypting (a second key).
  - **How it crept in (git timeline — great exam story):**
    1. `a2ab6fc` (12 Feb) SECRET_KEY hardcoded literal in code.
    2. `57a4f1c` (10 Mar) "removed secret key from codebase" — security fix: load from `.env` via godotenv.
    3. `2acff4c` (10 Mar) "make key pass tests" — re-added the hardcoded fallback string as a quick win so tests passed without a `.env`.
    4. `3c649da` (10 Apr) "add Docker Swarm support" — added `/run/secrets` reading, but wired only `DATABASE_URL` to it; `SECRET_KEY` left behind the `.env` gate.
    Lesson: a security fix + a rushed test patch + an infra migration that didn't reconcile = a regression. Not one big mistake.

## Build / Docker
- **Unnecessary build deps.** Dockerfile sets `CGO_ENABLED=1` + installs `build-base` + `sqlite-dev` for SQLite, but the prod binary uses **Postgres only** (pure-Go `pgx` driver — no C needed). SQLite is imported in `main_test.go` (tests) AND in `flag_tool.go` (a CLI helper carrying `//go:build ignore`) — both excluded from `go build .`, so neither reaches the prod binary. **Verified:** `CGO_ENABLED=0 go build .` produces a working, statically-linked binary. → Drop CGO + the C tools for a smaller static image. (Correction: earlier I said "SQLite is test-only" — wrong, `flag_tool.go` also imports it; the real reason it's excluded is the ignore build tag, not that it's a test.)
- **Dead volume.** `minitwit-db` volume declared in `docker-compose.yml` but no service uses it (relic of the old SQLite days).
- **Misleading log.** `main.go` logs "Listening on http://localhost:8080" *before* it binds, so a bind failure still prints "Listening".
- **Templates/static read from disk, not embedded.** App uses `ParseFiles("templates/...")` + `http.FileServer(http.Dir("static"))`, so the Dockerfile must copy both folders. Could use Go `//go:embed` to bake them into the binary → one self-contained file, nothing to forget to copy. Minor improvement, not wrong as-is.

## Infrastructure as Code (partial / untested)
- **Prod was provisioned manually, not by IaC.** `docs/operations/docker-swarm.md`: "A colleague had already provisioned the DO droplets." The `terraform/` was added later as the S12 exercise (`28491ba`) and "edited to match our current setup" (`c6b2309`) — written after the fact, never run to provision, not validated. So prod is a "snowflake server." **Stronger proof:** Terraform was added 12 May — 3 weeks AFTER the manual swarm runbook (21 Apr) — and it models **4 droplets with a self-hosted Postgres droplet**, while real prod is **3 nodes + DO managed Postgres**. The topologies don't match, so the Terraform demonstrably never produced the running infra.
- **README overstates it:** presents Terraform as *the* provisioning method ("this provisions all Droplets..."), but it's aspirational. Don't over-claim at the exam.
- Honest framing: early Hetzner VM = real Vagrant IaC; current prod = manual + descriptive-only Terraform. Fix: `terraform apply` into a fresh project to prove reproducibility; or document that prod is manual.
- Old `Vagrantfile` still in repo but legacy (Hetzner era, decommissioned). Dead-ish.

## CI/CD
- **Releases were manual + retrospective, not automated.** S04 task asked for automatic ≥weekly releases of what's in prod. Actual: created by hand in hindsight, picking the most important PRs. Honest gap — don't call it automated.
- **Only `test` is a required status check** (verified via GitHub ruleset "master lock"): master needs a PR + 1 review + the `test` job passing (no bypass, no force-push). BUT `lint`, `semgrep` (SAST), and `docker-scout` (CVE scan) run on the PR yet are **NOT required** — so a merge/deploy could proceed with failing lint/security/CVE. The quality+security gates are advisory, not blocking. Fix: add them to required checks.
- **`dev` has minimal protection** (only blocks force-push/deletion; no PR or CI). CI runs only on PR→master, so dev/feature work isn't CI-tested until the master PR.
- **CD rebuilds the image** instead of promoting the exact CI-tested image → tests one build, deploys another (same commit, so low risk, but not "build once, deploy that artifact").

## Config management
- **`.env` half-wired.** `.env` reaches `DATABASE_URL` (via `godotenv.Load()` in the package-init `getSecretKey()`), but `SECRET_KEY` only works when `.env` is present — so it's correct locally and broken in every containerized deploy. Config loading should be one consistent path.

## Testing / dev-prod parity
- **Parity gap.** Unit tests run on SQLite; prod runs on Postgres. SQLite-green ≠ Postgres-correct (SQL dialect differences). E2E tests (`docker-compose.test.yml`) do use Postgres, which softens it.
- **No one-command local DB.** Main `docker-compose.yml` has no Postgres service; you must run your own (we use a `minitwit-db` container on :5433).

## Monitoring / Logging
- **Reactive on the maturity model — proactive-grade tooling, operated reactively (self-assessed 1 Jun 2026).** We built app-level instrumentation (`minitwit_http_*`: p95 latency + error rate, not just CPU/disk = a Proactive trait per S06) and alerts to Discord (WebserverDown / HighErrorRate / SlowResponses), but the team rarely read the dashboards or drove decisions from them. Matches the S06 **Reactive** rung almost verbatim: "a small number of operationally-focused dashboards exist," data "needs to be transformed before it can be used." Honest exam line: *"We're reactive in practice; the gap to close isn't more tooling, it's making the existing data interpretable and part of our routine."*
- **Alerting never delivered to Discord (CONFIRMED by Leo: no notification ever arrived).** Likely root cause (from config; verify on live Grafana): the two halves were never connected. (a) `prometheus.rules.yml` has 3 alert rules, but `prometheus.yml` has no `alerting:` block and there's no Alertmanager → Prometheus evaluates rules with nowhere to route them. (b) Grafana has the delivery path (`contactpoints.yml` Discord webhook + `policies.yml`) but no provisioned Grafana alert rules → nothing feeds the contact point. Net: rules with no router + a router with no rules. Honest exam line: "we configured alerting but it never fired — the Prometheus rules and the Grafana contact point were never wired together." Fixable before Thu = a "diagnosed and fixed" story.
- **Loki/Promtail implemented but not understood (honest GenAI story).** The logging stack (Promtail → Loki → Grafana, S08) was built largely via AI without the team grasping how it works = exactly the "used a lot of AI, never understood it" gap. Being remediated during exam prep (1 Jun).
- **Monitoring vs Logging conflation risk.** Easy to blur the two at the exam. S06 Monitoring = metrics, "is something wrong?" (Prometheus+Grafana). S08 Logging = text events, "WHY is it wrong?" (Loki+Promtail+Grafana). They share Grafana as the display, which is what blurs them.
- **Live find (1 Jun) — logging caught a bug the metrics are blind to (strong S08 exam example).** Prod "Webserver Logs" panel shows recurring `http: superfluous response.WriteHeader call from main.(*responseWriter).WriteHeader (main.go:50)` on stderr across all 3 replicas. Means `WriteHeader` is called more than once per response somewhere (our `responseWriter` wrapper, main.go:48-51, passes every call through line 50). Harmless to users but real noise + code smell. Perfect demonstration of the S08 thesis: it's not a 5xx, not slow, not down → `up`/`HighErrorRate`/`SlowResponses` all miss it; only the logs surface it. Root cause not yet investigated.
- **Prod logging is more built-out than "barely used" implies.** Real multi-panel dashboard (All Logs / Webserver Logs / Error Logs), swarm labels populated, surfacing actual bugs. Supports the "proactive-grade tooling, reactive operation" framing: the capability is there; the gap is routine use, not tooling.
- **Logging dashboard has two real query weaknesses (verified from logging-dashboard.json + live logs, 1 Jun) — good "what we'd improve" ammo:**
  - *Log Volume by Service* uses a hardcoded `count_over_time({swarm_service=~".+"}[1m])`. The `[1m]` is fixed, so at wide ranges Grafana spaces points ~20 min apart but still counts only 1 minute each → under-samples ~95% of the time and the chart misrepresents volume. Also trips Loki query limits over 30d (red ⚠️ on panel). Fix: `[$__auto]` so the window scales with the view.
  - *Error Logs* uses `{swarm_service=~".+"} |~ "(?i)(error|fatal|panic)"` → substring-greps "error" across ALL services incl. Loki itself. Result: panel fills with Loki's own benign `rpc error: context canceled` query-cancellation chatter (none from the app), and the panel's own heavy query causes more cancellations = observer feedback loop. Fix (query, ships now): scope to the app — `{swarm_service="minitwit_webserver"} |~ "(?i)(error|fatal|panic)"`. Proper fix needs the app to log structured levels first: it currently uses only stdlib `log` (unstructured, no `level=` field — verified main.go/db.go/sim_api.go), so reliable level filtering would mean adopting e.g. Go `log/slog`, then `| logfmt | level="error"`. That two-layer answer IS S08's "use log levels" principle, motivated by a real gap.
- **App-level logging is nearly empty (verified live in Explore, 1 Jun).** Query `{swarm_service="minitwit_webserver", stream="stderr"} != "superfluous"` over 90 days → only ~45 lines, almost all `Listening on http://localhost:8080` startup messages. Go's stdlib `log` writes to stderr, so this captures ~all of the app's own logging → the app emits almost no intentional diagnostic logs (no request logging; handler errors only via the odd `log.Printf`). Nearly all real log value comes from Traefik access logs; the app itself isn't instrumented. Improvement: structured logging (`log/slog`) of real events (failed logins, slow queries, handler errors) so logs can answer "why". Ties to S08 "log what's necessary" (here: under-logging) + the reactive-maturity framing. Bonus: each `Listening` line ≈ a deploy/restart, so the log-volume chart doubles as a rough restart timeline.
- (Dashboard-as-code) **Also: editing the panel in the Grafana UI won't persist.** Dashboards are provisioned as code (logging-dashboard.json baked into the grafana image; dashboards.yml sets `allowUiUpdates: false`), so UI saves are blocked and overwritten on redeploy. Real change = edit the JSON in the repo → commit → CD redeploys. "Dashboards as code." Same principle as the hand-made-vs-provisioned alert-rules gap noted elsewhere.
